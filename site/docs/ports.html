Ports & adapters

The core never touches the outside world directly. Time, randomness, the network, storage and the app's lifecycle all come through ports: traits the platform implements and the core calls.

What a port is#

A port is a Rust trait marked #[undra::port]. The platform implements it (an adapter), or a Rust fake does in a test. The core calls it through the context, for example ctx.http().request(req).await, and does not know or care what is behind it. That is what keeps the core deterministic (rule R12): it has no wall clock, no random source and no threads outside the Clock, Rng and Timer ports and the runtime.

There are three kinds, and the kind decides how a call travels:

KindMeaning
syncthe platform answers before the call returns. A port is sync only if every method is sync
asyncthe platform answers later; the core's task waits, and can be cancelled
eventfire and forget from the platform into the core, such as "connectivity changed"

The ten standard ports#

PortKindMethods
Clocksyncnow_ms() -> i64, monotonic_ns() -> u64
Rngsyncfill(len) -> Bytes
Logsynclog(level, target, message)
Httpasyncrequest(HttpRequest) -> Result<HttpResponse, HttpError>
Kvasyncget, set, delete, list(prefix)
SecureStoreasyncthe same shape as Kv, for secrets
Fsasyncread, write, delete, list, each returning Result<_, FsError>
Timersyncset(timer_id, delay_ms); the platform answers later with a timer-fired event
Connectivityeventchanged(online, kind) with NetKind of Wifi, Cellular, Wired, Unknown or None
Lifecycleeventchanged(state) with AppState of Active, Inactive or Background

They exchange a small set of types: HttpRequest (method, url, headers, optional body, optional timeout), HttpResponse (status, headers, body), HttpError (Network, Timeout, Cancelled, InvalidUrl), Header, FsError (NotFound, Denied, Io), NetKind and AppState.

These ports and types ship inside each platform runtime and are not generated into your app's bindings. Every core links undra-ports, so its schema contains them and the schema hash covers them, but the generator leaves them out and the generated code refers to the runtime's own types. That is why your app can have its own record called Timer or Log.

Default adapters#

Each runtime ships an adapter for every port, so a new app works without adapter code.

PortSwiftKotlin (Android)TypeScript (browser)

Kvfiles in Application Supportfiles in filesDirIndexedDB

Clock, Rng, LogFoundation, SecRandom, os_logSystem, SecureRandom, android.util.Logbuilt in

Every default store is per core namespace (<namespace>/kv under the app's undra directory in Application Support or filesDir, a Keychain service or Keystore alias and an IndexedDB database named after it), so two cores of one app never read each other's keys, secrets or files; an adapter you pass yourself keeps the location you gave it.

On Android one call installs all ten, AndroidPlatformDefaults.install(core, context); the runtime alone installs only Clock, Rng, Log and Timer. On the JVM without Android, Connectivity and Lifecycle are stubs. On the web, Clock, Rng and Log are bound to imports of the wasm module, so a web app needs no adapter code for them.

Under React Native, loadNative installs all ten too: Kv, SecureStore, Fs and Connectivity are native code in @undra/react-native (files in the app's private storage, the Keychain or the Android Keystore, NWPathMonitor or ConnectivityManager, with the Swift and Android adapters' file layouts), Http is React Native's fetch and Lifecycle its AppState (docs/REACT_NATIVE.md).

Supplying your own adapter#

You replace a default when you load the core. The playground replaces Http with an in-memory server (so it needs no backend) and Kv with a map:

web/src/undra.ts
const adapters = { http: server, kv: memoryKv() };
await UndraPlaygroundCore.load({
  mode: "wasm-main",
  wasm: new URL(wasmUrl, location.href),
  adapters,
});
ios/PlaygroundApp/UndraBootstrap.swift
let adapters = Adapters.platformDefault
    .removing(portId: fnv1a32("port.Connectivity"))
    .replacing(PlaygroundNetwork.shared)
    .replacing(KvAdapter(directory: store))
try UndraPlaygroundCore.load(.inproc(adapters: adapters))
android/.../UndraApp.kt
val core = UndraPlaygroundCore.load(
    LoadOptions(mirror = MirrorOptions(framePacer = ChoreographerFramePacer())),
)
// Http, Kv, SecureStore, Fs, Connectivity and Lifecycle: the real adapters, nothing faked.
AndroidPlatformDefaults.install(core, this)

On Android the playground keeps every default: its Remote tab talks to a small HTTP server on the device's loopback interface, through the real Http adapter. To replace one port there, register another implementation after install (core.registerPort(StandardPorts.Http.PORT_ID, impl)).

Register the ports your core needs when you load it. A core's start-up work (query hydration reads the Kv port) runs as soon as the runtime exists. It asks for Kv every 100 ms for five seconds, so adapters registered right after the load (Android's install) are in time; a port registered later than that is missed, and the cache then starts empty.

Your network stack inside#

The defaults above are the platform's own. If your app has a network stack of its own (a token that is refreshed, interceptors, tracing, certificate pinning), a request the core makes through a default adapter does not go through it: on Android HttpURLConnection is OkHttp underneath, but the platform's instance, not your OkHttpClient. Hand your stack to the three network ports instead (Http, WebSocket, Sse) and every request the core makes goes through it. You do not write the adapters: the contract the core relies on (typed errors, a timeout that covers the body, cancellation that closes the socket, a size cap, streams that stop the server when the core stops reading) is already implemented, and the same test suites check it on each.

PlatformYou passYour stack applies
Androidyour OkHttpClient, to the optional okhttp-adapters moduleinterceptors, Authenticator (a 401 is answered with a refreshed token and the request goes again), event listeners, CertificatePinner, Dns, proxy, cookie jar, dispatcher (a WebSocket's upgrade is the exception OkHttp makes: your application interceptors see it, your network interceptors and event listener do not)
iOS and macOSyour URLSession, to HttpAdapter, URLSessionWebSocketAdapter and URLSessionSseAdapterits configuration and URLProtocol classes, its delegate (server trust and pinning, authentication challenges), proxy, cookies
Webyour fetch and WebSocket, to fetchHttp, fetchSse and browserWebSocketwhatever your wrapper does to a request: a token, a retry on 401, a trace header
React Nativenothing: reactNativeHttp() is React Native's fetchReact Native's own networking module, so what the app configures there
kotlin
// In place of AndroidPlatformDefaults.install(core, this): the same ten ports, and Http, WebSocket and Sse go through your client.
AndroidPlatformDefaults.installWithOkHttp(core, this, appGraph.okHttpClient)
swift
let adapters = Adapters.platformDefault
    .replacing(HttpAdapter(session: session))
    .replacing(URLSessionWebSocketAdapter(session: session))
    .replacing(URLSessionSseAdapter(session: streamingSession)) // same delegate, a configuration that lets a stream be quiet
ts
const adapters = { ...browserAdapters(), http: fetchHttp({ fetch: appFetch }) };
const ports = {
  [OptInPortIds.WebSocket.portId]: webSocketPort(browserWebSocket({ WebSocket: AppWebSocket })),
  [OptInPortIds.Sse.portId]: ssePort(fetchSse({ fetch: appFetch })),
};

The pieces and the places they differ from the defaults are documented where they live: the okhttp-adapters README (redirects, retries and timeouts are your client's; a WebSocket on OkHttp repairs malformed UTF-8 in a text frame instead of failing the connection, and OkHttp tells neither your event listener nor your network interceptors about a WebSocket's upgrade; a stream is opened on a client derived from yours with no read timeout and HTTP/1.1), and the cookbook recipe, with the code of all three. The decision is ADR-060.

When a port is missing#

An unavailable port is a normal outcome, not a bug. A port nobody registered behaves as unavailable, a call can be cancelled, and a host can reply with bytes that do not decode. The core handles all three without panicking:

  • If the port method returns Result<T, E>, the failure becomes an E. HttpError and FsError implement From<PortError>, so an unavailable Http port is Network("the Http port has no adapter registered (E0062: register one, see ..)"), with the code and the link to the fix. Your own error type needs the same conversion, and the macro checks it at compile time (E0033).
  • If the method has no error channel, there is no typed way to say "unavailable", so the call panics with a message that names the port and method and says how to bind one (E0062, in the shape of every diagnostic: what, why, fix, docs link). The runtime contains that panic at the boundary. Give optional ports a Result, or register them.

Writing your own port#

Mark a trait with #[undra::port]. The macro registers it in the schema and generates a proxy type, so the core calls your trait like any other, and the platform gets a protocol or interface to implement. This one is made up, to show the shape:

rust
#[undra::port(sync)]
pub trait Haptics {
    fn tap(&self, strength: u8);
}

A port method's parameters must be wire types (E0030), and an event port's methods cannot return a value (E0031).

Testing with fakes#

Every standard port has a deterministic Rust fake in undra::ports::fakes. They are all Send + Sync, keep state behind a lock, and never read the system clock, a random source or a thread.

FakePortBehaviour
FakeHttpHttpscripted replies chosen by a matcher; every request recorded
MemKv, MemSecureStoreKv, SecureStorein-memory ordered maps; operations recorded
MemFsFsin-memory tree with the platform adapters' error semantics
FakeClockClock and Timersettable time; advance fires due timers
SeededRngRngxorshift64*; the same seed gives the same bytes
CaptureLogLogkeeps every record
ScriptedConnectivity, ScriptedLifecycleConnectivity, Lifecyclepush scripted events into a runtime

TestRuntime::new() runs the executor on the test thread and lets you drive it with run_until(fut) and run_pending(). Installing the fakes binds all of them into it. The doctest of FakeHttp shows the style:

rust
use undra_ports::{Http, HttpError, HttpRequest, HttpResponse};
use undra_ports::fakes::FakeHttp;
use undra_runtime::testing::TestRuntime;

let http = FakeHttp::new();
// A flaky endpoint: two timeouts, then success for ever after.
http.respond_sequence("https://x.test/a", [Err(HttpError::Timeout), Err(HttpError::Timeout)]);
http.respond("https://x.test/a", HttpResponse::new(200, b"ok".to_vec()));

let t = TestRuntime::new();
let get = || HttpRequest::get("https://x.test/a");
assert_eq!(t.run_until(http.request(get())), Err(HttpError::Timeout));
assert_eq!(t.run_until(http.request(get())), Err(HttpError::Timeout));
assert_eq!(t.run_until(http.request(get())).unwrap().status, 200);
assert_eq!(http.call_count(), 3);

Time works the same way. FakeClock is the single source of time for both Clock and Timer, so ctx.sleep asks for a timer and advancing the fake clock serves it: sleeps wake at exactly their deadline. On a runtime with the fakes installed, advance time with Fakes::advance, not TestRuntime::advance.

The platforms get the same treatment. The contract scenarios run every platform runtime against the real core with a manual clock, an in-memory Http server, an in-memory Kv and a test that emits connectivity events itself.

The test kit puts these fakes behind the real core in Swift, Kotlin and TypeScript too, with a manual clock, and replays recorded port traffic: Testing your app.
