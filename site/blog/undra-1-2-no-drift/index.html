Undra 1.2: no drift between iOS, Android and the web

One Rust core already made three hosts agree on their logic, state and data. What still drifted was everything the schema cannot see: which calls each UI makes, what each platform's adapters send, how a custom port is written three times. 1.2 is about those three things.

9 Oct 2026 · 6 min read · Undra team

What still drifted

A team spent a week building a trading app on Undra 1.1: one core, SwiftUI on iOS, Compose on Android, React on the web. The core was never the problem. Three things were, and each of them lived outside the schema:

  • A header the replay never saw. Their production API refused a request that every test had accepted: one platform's adapter sent Accept twice. Their replay server matched on method and URL alone, so the duplicate got through.
  • A wrong host on one platform. Orders went to the API host instead of the web host, on one platform only, and nothing compared what the three hosts asked for.
  • A port that did not compile. Their iOS credentials port, a plain class conforming to the generated protocol, failed to build under Xcode 26's default main-actor isolation, and the file also needed an import nobody had told them about.

The first two are drift at the boundary: the core is deterministic, so if the three apps fed it the same inputs they would have ended in the same state. The third is drift in the one piece of host code a schema cannot generate for you. 1.2 answers each.

undra drift

Undra's testing kit already records a session as one JSON document, the same format on every platform: the calls the host made, the replies, every change-set, every port call and its answer, every event the host pushed. undra dev --record writes one for the app it is serving. 1.2 adds the comparison:

shell
$ undra dev --record ios.json          # the iOS app connected
$ undra dev --addr 127.0.0.1:7444 --record android.json   # the Android app, on a second server
$ undra drift ios.json android.json web.json
Drift: ios.json (reference) against android.json, web.json (schema 0x437ce0973ce54a88)
ignored: Clock and Rng replies, Timer arguments, Idempotency-Key headers

android  calls     Todos.add #2: missing on android (ios sent {"title": "Walk the dog"})
web      ports     Http.request #1 req.headers: accept appears twice on web

2 divergences on 2 of 3 recordings

The first file is the reference; every other file is compared with it. What is compared: the calls each host made and their order, with the arguments decoded through the project's schema; what each platform's port adapters answered, per port and method; the events each host pushed (connectivity, lifecycle); what was observed; and the state every store ended in. What legitimately differs between two runs is ignored and said so in the report: clock and random readings, timer ids, idempotency keys, timestamps. Handles are aligned by the constructor that made them and its ordinal, so a store created second on iOS is compared with the store created second on Android, whatever number each runtime gave it. With --exit-code the command fails on any divergence, which is how it goes into CI.

The duplicate Accept and the wrong host are both port drift: the Http.request each platform's core asked for was the same, and the comparison of what the adapters sent is where they would have shown. The record format is unchanged, so a recording made with 1.1 reads in 1.2.

A port that compiles on every platform

A custom port in Rust is a trait. On Kotlin it is an interface and on the web an object literal, and both compiled from day one. On Swift the generated protocol is Sendable with nonisolated requirements, because the core calls it from its own thread, and an app class under default main-actor isolation is @MainActor: a synchronous witness on the main actor cannot satisfy a nonisolated requirement, so the conformance fails to compile. Marking the class nonisolated fixes it, but nothing told the author that.

1.2 generates a second form beside the protocol: one function per port that takes a @Sendable closure per method. A @Sendable closure is nonisolated under every isolation mode, so there is nothing to conform to and nothing to annotate:

swift
import UndraRuntime

let locale = localePortImpl(hello: { "Bonjour" })
let core = try UndraPlaygroundCore.load(.inproc(adapters: .platformDefault.replacing(UndraIds.Ports.Locale.portId, locale)))

The protocol form stays, for a port with state worth a type, and its generated doc now says what to import and when to write nonisolated. A compile test in CI builds both forms with -default-isolation MainActor, so the shape cannot regress. The cookbook has the same port on three platforms, with each snippet compiled by CI, and the playground's iOS app implements its Locale port in the new form. The decision is ADR-066.

The merge gate in half the time

Nothing lands on main unless every workflow is green on the exact commit. That gate took 26 to 31 minutes on the last three green runs, and the numbers said why: five macOS runners serve the whole queue, and four jobs ran their work in a row where nothing depended on the order (the macOS Bazel example ran four Bazel configurations one after another, 23 minutes; the Rust job's cargo test --workspace spent two thirds of its 11 minutes in the CLI's integration tests; the Swift job built the Xcode projects after the runtime's tests; Two cores built its Debug cores, then its Release cores).

Each of the four is now two jobs that run side by side, with the same steps between them and nothing dropped. The Bazel jobs are split by ruleset set rather than by Bazel version, so each job's 9.x run reads what its 8.8.1 run built from a disk cache. The macOS jobs are listed first, longest first, so they get runners first. Every job still runs on every change, because a job that can be skipped cannot be part of the roll-up. The record, with the measurement from the release's own run, is ci-wall-time.md.

What is next

The duplicate header pointed at something undra drift reports but does not fix: the platform default adapters themselves differ. The five SSE adapters merge the core's headers in different ways, and the JDK Http adapter drops restricted headers where Swift passes them. The next step is a conformance file for the real adapters, recorded against one server and diffed in CI, the way the fakes are already held to one file. It needs a rule in the specification first (which header wins), so it is on the roadmap under Next, with the evidence.

Upgrading

undra upgrade moves a project's pins to 1.2.0 and prints the release's migration notes. Nothing on the wire, the ABI or the schema changed; bindings regenerate to the same public shapes plus the new Swift port builders. The testing page has the drift command, the ports page the three-platform port, and the roadmap what shipped and what is open.
