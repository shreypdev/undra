# Review: bazel-compat (Bazel 8.8 and 9.x, the lowest ruleset versions the rules need)

Date: 2026-10-05. Role: adversarial reviewer. Branch `wt/bazel-compat` (draft PR #33), reviewed at `41449f6` (cut from `main` `58e373a`);
the fixes are the commits after it on the branch. Record: `.10x/decisions/sde/bazel-compat.md`; ADR-061.

## Verdict

**CLEAN after the fixes below.** The claims reproduce: on this Mac (Apple silicon, Xcode, Bazelisk) Bazel 8.8.1 and 9.2.0 both pass the
rules' tests (3 of 3), the example's `bazel test //...` (6 of 6) and `//:mobile_ios`, with no `.bzl` change, at the minimums the piece
declares. One design defect (Medium): with the example pinned to the minimums, CI tested only the oldest rulesets. It is fixed: the
example is back at recent versions and `examples/bazel/scripts/at-minimums.sh` runs it at the minimums, so CI covers both ruleset ends
on both Bazels, Linux and macOS. Three Low findings are fixed too. Nothing is open against this piece.

## Checked, no finding

* **The minimums resolve exactly as declared.** `at-minimums.sh` with `--check_direct_dependencies=error` passes on 8.8.1 and 9.2.0, so no
  ruleset in the example's graph is raised above its minimum. Negative check: `apple_support` declared at 1.17.1 fails the run with "the
  root module requires module version apple_support@1.17.1, but got apple_support@1.24.2", and the example's MODULE.bazel is restored
  afterwards. The "forced by" rows (rules_apple by rules_swift 3.4.0, aspect_rules_js by aspect_rules_ts 3.10.0) are stated as such in the
  guide, as the author wrote them.
* **rules_rust 0.70.0 loses nothing the rules use.** The rules touch `@rules_rust//rust:toolchain_type`, `current_rust_toolchain` and the
  toolchain's `rustc`, `cargo` and `sysroot` (`bazel/undra/private/actions.bzl`, `core.bzl`); the example's `rust.toolchain` uses `edition`,
  `extra_target_triples` as a list, `sha256s` and `versions`. Host, web and iOS cores build at 0.70.0 on both Bazels. The Android core is
  not built anywhere, before or after this piece (ADR-061; `wt/ndk-input` changes that, below).
* **rules_kotlin 2.3.0 and `undra_android_library`.** `bazel build //android:hello --config=android` (`kt_android_library`, the Android SDK)
  builds at the minimums and at the recent versions, on 8.8.1 and on 9.2.0 (by hand; CI does not build it, as before). `bazel test //...`
  loads the `android` package, so a rules_kotlin that breaks it at loading fails CI.
* **The 9.2.0 literal and its bump note.** 9.2.0 (2026-07-13) is the newest final 9.x release; 9.3.0 is at rc4 (2026-10-01), checked today
  against the GitHub releases API: the record's statement is a fact, not a guess. The bump note in `ci.yml` now also names
  `examples/bazel/README.md`, the other place the literal is.
* **Docs agree.** `bazel/MODULE.bazel`'s comment, the example's MODULE.bazel and README, the guide's "Set up" and "Ruleset versions", the
  CI comments and the record say the same thing: minimums declared by the rules, recent versions in the example, both run on both Bazels.
  `node site/scripts/build-all.mjs` leaves no diff; `check-links.mjs`: 54 pages OK. `scripts/check-no-em-dash.sh` passes. No new text names
  an outside party (the telemetry lines that name one are older than this piece and unchanged). No step depends on machine speed.

## Observed, not a finding of this piece

One `//:mobile_ios` build on 9.2.0 failed once with Cargo's "No such file or directory" inside `/tmp/undra-bazel-<key>`; the same
build passed when run again. Another agent on this machine removed the `/tmp/undra-bazel-*` directories at about that time, which
explains it: that directory is the action's working directory (named by the target, so builds are reproducible across checkouts).
Not a defect of this piece, and nothing here changes `run.sh`.

## Merge order with `wt/ndk-input`

Land **bazel-compat first**: it is smaller and its conflicts with ndk-input are documentation only. A trial merge
(`git merge-tree` of this branch and `wt/ndk-input` `0181650`) conflicts in three files: `site/docs/bazel.html` (adjacent hunks: keep
ndk-input's rewritten "Why it is hermetic" list and the paragraph on what the machine provides, then this piece's "Ruleset versions"
section after them), `site/search-index.json` (regenerate: `node site/scripts/build-all.mjs`, which also rewrites `llms-full.txt`) and
`.10x/decisions/sde/_index.md` (keep both lines). `bazel/MODULE.bazel` (`use_repo(undra, ...)`), `examples/bazel/MODULE.bazel` (the
`rust.toolchain` block, `undra.android_std`, the NDK `http_archive`s) and `ci.yml` merge cleanly, because the example's `bazel_dep`
lines are back to what `main` has. After merging `main`, ndk-input should run its new targets at both ends on both Bazels:
`scripts/at-minimums.sh build //:mobile_android ...` and `//android:hello --config=android`, with `USE_BAZEL_VERSION` 8.8.1 and 9.2.0
(rules_kotlin's 2.3.0 floor is set by `undra_android_library` on Bazel 9, and the Android core is new under rules_rust 0.70.0), and
decide whether its Android job gets the same 9.x and minimums steps the other two Bazel jobs have. A `bazel_dep` it adds to the example
needs a minimum in `bazel/MODULE.bazel`, or `at-minimums.sh` refuses to run (it adds none today).

## Reproduce

```sh
source scripts/env.sh
R=$HOME/.cache/bazel-repository
for v in 8.8.1 9.2.0; do
  (cd bazel          && USE_BAZEL_VERSION=$v bazel test //tests/... --lockfile_mode=off --repository_cache=$R --test_output=errors)
  (cd examples/bazel && USE_BAZEL_VERSION=$v bazel test //... --lockfile_mode=off --repository_cache=$R --test_output=errors)
  (cd examples/bazel && USE_BAZEL_VERSION=$v bazel build //:mobile_ios --lockfile_mode=off --repository_cache=$R)
  USE_BAZEL_VERSION=$v examples/bazel/scripts/at-minimums.sh test //... --repository_cache=$R --test_output=errors
  USE_BAZEL_VERSION=$v examples/bazel/scripts/at-minimums.sh build //:mobile_ios --repository_cache=$R
  USE_BAZEL_VERSION=$v examples/bazel/scripts/at-minimums.sh build //android:hello --config=android --repository_cache=$R   # ANDROID_HOME
done
git status --short    # empty: neither the lock nor MODULE.bazel changed
```

All of it passed here, at the fixed head. `scripts/ci-local.sh --only ci/bazel-example,ci/bazel-example-macos,site/build` from a clone of `53d9071`: the first four Linux-job
steps passed (the rules' tests, `//...`, `//...` at the minimums, the rules' tests on 9.x); it was stopped during the fifth to wrap up
the review, and the steps after it are the commands above, already run in the worktree. On the author's head the hosted Linux job
("Bazel example", minimums on 8.8.1 and 9.2.0) was green.
