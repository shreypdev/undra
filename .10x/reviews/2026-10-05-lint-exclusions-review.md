## Verdict

**Merge after fixes; the fixes are on the branch.** The setting itself is right and small: one field on `bindgen::Plan`, one `if`
around `lint::fragments`, so the manifest, `--check` and pruning follow with no new code, and the switch both ways is clean (replayed
below). The error teaches (code, line, why, fix, the guide and `errors.html#C0002`), `undra init` writes the key as a comment, no
golden moved, and the Bazel rules really need no change. What was wrong was in what the piece tells a user to write instead: the
ktlint root section the guide gave (and the generated `.editorconfig` has suggested since the Bazel piece) does not match the
layout `undra init` makes. ktlint 1.8 proved it; it is fixed and now held by the Bazel example's lint test. Nothing above Low is open.

## What was verified, and how

* **Build gates:** `cargo test -p undra-cli` (all suites, before and after the fixes), `cargo clippy -p undra-cli --all-targets -- -D
  warnings`, `cargo fmt --check`, `scripts/check-no-em-dash.sh`, `node site/scripts/build-all.mjs` (no diff left, before and after the
  docs fix) and `node site/scripts/check-links.mjs` (54 pages). `undra-bindgen` is not touched by the piece; its tests were not re-run.
* **The switch.** Through the binary: `none` writes 37 files and a manifest without the four; `beside` and an absent key write the same
  37 plus the four; `--check` after a switch names exactly the four as stale; the next run removes them and `--check` is clean; back
  to `beside` writes them again. Every generated `.kt` keeps `@file:Suppress("ALL", "ktlint")` under `none`.
* **`undra upgrade`, `undra init`, `undra adopt`.** `upgrade` regenerates through `commands::bindgen::run`, so it reads the project's
  setting; nothing else in the CLI reads or writes the lint files (searched). `init` and `adopt` take the setting from the config they
  write (the default); `render` writes the key only when it is `none`, and parse/render round-trips both.
* **The error (R8).** `"all"`, `"None"`, `""`, `false` and `"everywhere"` (through the binary): `error[undra::C0002]`, the file and
  line, the why, both spellings in the fix with the guide's anchor, `errors.html#C0002`, nothing written.
* **Bazel.** `run.sh` runs `undra bindgen -C <project> --library .. --out <fresh dir>` over the declared `undra.toml`; the tree outputs
  are directories, the srcjar takes `*.kt` only and the Swift check lists `Sources/**/{*.swift,*.c,*.h,module.modulemap}`: no output,
  list or test names a lint file. After the fixes, `bazel test //tests/...` in `bazel/` (3 tests) and `bazel test //...` in
  `examples/bazel` (6 tests, the Swift one included) pass on this Mac.
* **Goldens.** None weakened; the one golden that moved (`tests/golden/stores/kotlin/.editorconfig`) moved with M1, and its five copies
  in the examples are byte-identical to what the branch's CLI writes.
* **Wording.** No em-dash, no outside party named in the diff, the record or the commits; every new `pub` item is documented.
* **Tests and machine speed.** The new tests compare files and text only; none waits or times anything.

## The root-configuration lines, tool by tool

* **ktlint** (`.editorconfig` `[generated/**]`): run, ktlint 1.8.0, and now a Bazel test. The Gradle filter
  (`exclude { it.file.path.contains("/generated/") }`) matches ktlint-gradle's documented `filter { exclude { .. } }` shape; not run.
* **SwiftLint** (`excluded: - generated` in the root `.swiftlint.yml`): `excluded` paths are relative to the configuration's directory,
  per SwiftLint's documentation. Not run (not installed).
* **ESLint 9** (`{ ignores: ["generated/**"] }` alone in an object): a global ignore, relative to `eslint.config.js`, per ESLint's
  flat-config documentation. **ESLint 8** (`"ignorePatterns": ["generated/"]`, or `.eslintignore`): gitignore-style, relative to the
  configuration. Not run (not installed; nothing downloaded).
* **Vale** (`[generated/**]` with `BasedOnStyles =` after the section that matches the sources): could not be checked against a run,
  and from the documentation alone I cannot confirm either half (that an empty `BasedOnStyles` clears the styles a broader section
  set, and how Vale orders two sections that both match). The page already says Vale is not run; it stays a documented, unverified
  line.
