| I1 | Info | The SSE bound. `SseParser` dispatches only in `apply` on an empty line, and only with `hasData` (`SsePort.swift`, `dispatch`), so an event needs the end of a `data` line and the end of a blank line. In one chunk the first event may have had its `data` line ended by earlier bytes (one line end), every later one needs two. `mostEvents` counts every LF and CR as a line end and returns `1 + (n - 1) / 2`: a CR LF pair counts two for one line, a lone CR one, a LF after the chunk before ended in CR (skipped by `consume`) one for none, a comment line or an `id`/`event`/`retry` line one for no event, a chunk that ends mid-line counts its line ends only (the partial line completes in the next chunk, where its end is counted), a partial BOM followed by a line end throws before it dispatches. So the count is never below what the bytes complete. The `limit` stop returns exactly `limit` once `2 * limit - 1` line ends are seen, and `waiting + limit >= room` for `limit == room`. The seeded test (`SseParserBoundTests`, 3,000 bodies cut anywhere, with CR, CR LF, CR CR, comments, multi-line `data`, bare lines) checks the same on the real parser. | verified by reading and by the suite |
| I2 | Info | Read-ahead bound: after a chunk parsed with the task running, `waiting <= waiting_before + most < room`; a chunk that may reach `room` is suspended before its parse as before; `receive` is serialised by URLSession's delegate queue. The queue is still at most `room` plus one chunk's events plus the chunks in flight, as the class comment says. Suspend and resume: `receive` suspends only when `!suspended`, resumes only when `suspended` (failure, or `parsing == 0 && waiting < room`); `nextEvent` resumes only when `suspended && parsing == 0 && waiting < room`; `close` and `cancelRead` resume once when `wasSuspended`; a chunk after `over` or `end` neither suspends nor parses. A non-UTF-8 chunk parsed with the task running now cancels without a resume, which is right for a running task. | verified by reading |
| I3 | Info | The residual the record owns up to (a chunk whose line ends reach the mark without ending events, the consumer at the mark, as the body ends): with `room` 16 such a chunk needs 31 line ends that end no event, which only a comment flood or a multi-line `data` event gives as the stream ends.
